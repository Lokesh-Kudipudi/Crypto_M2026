Hashing

Owner: Suresh. Fixed-size fingerprints that can't be reversed.

SHA-256

Input: any lengthOutput: 256 bitsUsed for: PDF hash, token hashStandard: FIPS 180-4

SHA-256 uses the Merkle–Damgård construction. It splits the message into 512-bit blocks and feeds each one, along with the current 256-bit state, through a compression function.

Initial stateH0
→
Compressblock 1
→
Compressblock 2
→
…block n
→
Digestfinal state

Step 1: Padding

Append the byte 0x80, then zero bytes, then the message's length in bits as a 64-bit number, so the total is a multiple of 64 bytes. Including the length stops messages from sharing a padded form.

Step 2: Constants

The starting state is the first 32 bits of the fractional parts of the square roots of the first 8 primes. The 64 round constants come from the cube roots of the first 64 primes. Using such public values shows no hidden weakness was chosen. This page computes them that way.

Step 3: Message schedule

The 16 words of a block are expanded to 64, so that each input bit affects many rounds:

W[t] = σ1(W[t-2]) + W[t-7] + σ0(W[t-15]) + W[t-16]    (mod 2^32)
σ0(x) = ROTR 7(x)  XOR ROTR 18(x) XOR SHR 3(x)
σ1(x) = ROTR 17(x) XOR ROTR 19(x) XOR SHR 10(x)

Step 4: 64 rounds

Eight registers, a to h, start from the state. Each round computes:

Σ1(e)     = ROTR 6(e) XOR ROTR 11(e) XOR ROTR 25(e)
Ch(e,f,g) = (e AND f) XOR ((NOT e) AND g)       e chooses between f and g
T1        = h + Σ1(e) + Ch(e,f,g) + K[t] + W[t]

Σ0(a)     = ROTR 2(a) XOR ROTR 13(a) XOR ROTR 22(a)
Maj(a,b,c)= (a AND b) XOR (a AND c) XOR (b AND c)  the majority of each bit
T2        = Σ0(a) + Maj(a,b,c)

h=g  g=f  f=e  e=d+T1  d=c  c=b  b=a  a=T1+T2

The mix of addition (non-linear over XOR), rotation (spreads bits) and Boolean functions (non-linear per bit) creates the avalanche effect.

Step 5: Feed-forward

The registers are added to the block's starting state. This makes the compression function one-way: even someone who could run the rounds backwards wouldn't know which starting state to subtract.

Security

  • Preimage: about 2256 work. Collision: about 2128 work, because of the birthday bound.
  • Length extension: knowing H(m) allows computing H(m || padding || x) without knowing m. So SHA-256(secret || message) is unsafe as a MAC, which is why HMAC exists. The project doesn't use that pattern.

Tokens and claim codes

Token: 256 bitsClaim code: about 98 bitsStored as: SHA-256 hash

These rely on entropy. A secure random generator makes every value equally likely, so an attacker has no better strategy than trying values at random.

Token:      randomBytes(32) → cookie or share link
Stored:     SHA-256(token)
Claim code: 20 characters from a 30-character alphabet
Entropy:    20 × log2(30) ≈ 98.1 bits

The hash doesn't need to be slow. At a trillion guesses per second, searching all 298 claim codes would take about 10 billion years, and rate limiting stops online guessing long before that.

Rejection sampling

A random byte has 256 values, and 256 isn't a multiple of 30. Using byte % 30 directly would make the first 16 characters slightly more likely (9 in 256, against 8 in 256). So bytes of 240 or above are thrown away, because 240 is exactly 8 × 30. Every character is then equally likely.

HMAC and PBKDF2

Inside scryptHMAC: RFC 2104PBKDF2: RFC 8018

The project doesn't call these directly, but scrypt starts and ends with them.

HMAC(K, m) = SHA-256( (K XOR opad) || SHA-256( (K XOR ipad) || m ) )
ipad = 0x36 repeated, opad = 0x5c repeated, K padded to 64 bytes

PBKDF2 block i = HMAC(password, salt || INT(i)), then XORed with c - 1 more HMAC iterations

The nested hash removes the length-extension problem. scrypt uses PBKDF2 with just one iteration (c = 1), since memory-hardness comes from the step in the middle. PBKDF2 simply stretches and compresses the data here.

scrypt

Used for: passwordsN = 2^15, r = 8, p = 1Memory: 32 MiBStandard: RFC 7914

scrypt is a memory-hard function. GPUs and custom chips run hashes cheaply in parallel, but memory is expensive to multiply. So each guess is made to need a lot of it.

PBKDF2Password and salt become a block B
→
ROMixFill memory, then read it at unpredictable positions
→
PBKDF2Password and mixed B become the output

ROMix: the memory-hard core

X = B
for i = 0 to N-1:      V[i] = X;  X = BlockMix(X)        fill N blocks
for i = 0 to N-1:      j = Integerify(X) mod N
                       X = BlockMix(X XOR V[j])          read an unpredictable block
return X

The value of j depends on the current data, so it can't be known in advance. An attacker who skips storing V has to recompute blocks when they're needed, which costs far more time. Reducing memory costs extra time, and the product of the two stays high.

BlockMix

BlockMix runs Salsa20/8 across the 2r 64-byte pieces of a block, each chained to the one before, and then shuffles the outputs. Here a block is 128 × r = 1 KiB.

X = B[2r-1]
for i = 0 to 2r-1:  X = Salsa20/8(X XOR B[i]);  Y[i] = X
output = Y0, Y2, ..., Y[2r-2], Y1, Y3, ..., Y[2r-1]

Salsa20/8

This is a fast 64-byte scrambler made of only addition, rotation and XOR. It treats the input as 16 words and applies four-word "quarter rounds", first down columns and then along rows, for 8 rounds in total:

b ^= (a + d) <<< 7
c ^= (b + a) <<< 9
d ^= (c + b) <<< 13
a ^= (d + c) <<< 18

Encryption

Owner: Rishitha. Hiding data with a key, and detecting changes to it.

AES-256

Block: 128 bitsKey: 256 bitsRounds: 14Standard: FIPS 197

AES is a substitution-permutation network. It arranges 16 bytes in a 4 × 4 grid, filled column by column, and alternates confusion (hiding the link to the key) with diffusion (spreading each bit's influence).

The four operations

OperationWhat it doesPurpose
SubBytesReplaces each byte using the S-box: its inverse in GF(28), followed by an affine transformThe only non-linear step, which stops algebraic attacks
ShiftRowsRotates row r left by r positionsMoves bytes between columns
MixColumnsMultiplies each column by a fixed matrix in GF(28)Each input byte affects all 4 output bytes of its column
AddRoundKeyXORs in that round's 16-byte keyThe only step that uses the key

Round structure

AddRoundKey(0)
Rounds 1 to 13:  SubBytes → ShiftRows → MixColumns → AddRoundKey
Round 14:        SubBytes → ShiftRows → AddRoundKey     no MixColumns

After two rounds, every output byte depends on every input byte.

Arithmetic in GF(28)

Bytes are treated as polynomials with bits as coefficients. Addition is XOR. Multiplication works modulo x⁸ + x⁴ + x³ + x + 1 (0x11B). Multiplying by 2 is a shift, followed by XOR with 0x1B if the top bit was set.

MixColumns:  [ 2 3 1 1 ]
             [ 1 2 3 1 ]  × column
             [ 1 1 2 3 ]
             [ 3 1 1 2 ]

Key schedule

The 32-byte key expands into 15 round keys, made of 60 four-byte words:

w[i] = w[i-8] XOR f(w[i-1])
every 8th word:      f = SubWord(RotWord(x)) XOR Rcon
i mod 8 = 4:         f = SubWord(x)
otherwise:           f = x

Security

The best known attacks on full AES-256 are only slightly better than trying every key (about 2254). Grover's quantum algorithm would reduce the effective strength to about 128 bits, which is still considered secure.

GCM mode

Type: AEADIV: 96 bitsTag: 128 bitsStandard: NIST SP 800-38D

GCM combines counter mode for confidentiality and GHASH for authentication. AES only runs forward, even for decryption.

Part 1: Counter mode

J0        = IV || 00000001                  reserved for the tag
Counter i = IV || (i + 1)                   data starts at counter 2
C[i]      = P[i] XOR AES(K, Counter i)

Part 2: GHASH

GHASH treats 16-byte blocks as elements of GF(2128), using the polynomial x¹²⁸ + x⁷ + x² + x + 1. Addition is XOR, and each step multiplies by a secret value H:

H    = AES(K, 16 zero bytes)
Y0   = 0
Y[i] = (Y[i-1] XOR block[i]) × H           AAD blocks, ciphertext blocks, then a lengths block
S    = final Y
Tag  = S XOR AES(K, J0)

This evaluates a polynomial at the secret point H. Without H, an attacker can't predict the tag of changed data. The forgery chance is about L / 2¹²⁸ for a message of L blocks. The mask AES(K, J0) hides H-related information from the output.

Why an IV must never repeat

C1 XOR C2 = P1 XOR P2                      the plaintexts leak
Tag1 XOR Tag2 = polynomial in H             the attacker can solve for H, then forge

With random 96-bit IVs, NIST limits use to about 232 messages per key. The project's PDFs each get their own key, so an IV repeat isn't a realistic concern for them.

Digital signatures

Owner: Nanda. Proving who approved something.

Elliptic curves

Curve: secp256k1y² = x³ + 7Security: about 128 bits

Points on the curve form a group. There's a rule for adding two points that gives a third, all with arithmetic modulo a prime p.

Adding P and Q:   λ = (y2 - y1) / (x2 - x1)
Doubling P:       λ = 3·x1² / (2·y1)
Then:             x3 = λ² - x1 - x2
                  y3 = λ(x1 - x3) - y1

Geometrically, a line through P and Q meets the curve at a third point, and reflecting that point over the x-axis gives the sum. Over a finite field, the picture becomes scattered points, but the algebra still holds.

Scalar multiplication

Computing k × G doesn't need k additions. Double-and-add reads k's binary digits and takes only about 256 doublings and 128 additions for a 256-bit k.

The hard problem

Given Q = k × G, finding k is the elliptic curve discrete logarithm problem. The best known classical attack, Pollard's rho, takes about √n steps, so about 2128 on this curve. Shor's algorithm on a large quantum computer would break it.

ECDSA

Used for: batch and wallet signaturesSignature: r, s, vStandard: SEC 1, FIPS 186
Key pair    private d,  public Q = d × G

Sign z      choose secret k
            R = k × G
            r = R.x mod n
            s = (z + r·d) / k  mod n

Verify      u1 = z / s,  u2 = r / s
            R' = u1 × G + u2 × Q
            valid if R'.x mod n = r

Why verification works

R' = (z/s) × G + (r/s) × (d × G)
   = ((z + r·d) / s) × G
   = k × G                 because s = (z + r·d) / k
   = R

The secret k

k must be unique and unpredictable. Two signatures with the same k reveal the private key:

k = (z1 - z2) / (s1 - s2)  mod n
d = (s·k - z) / r  mod n

Wallets typically derive k deterministically from the key and message (RFC 6979), so it isn't exposed to a faulty random generator. In this project, MetaMask does the signing, and our code never touches k.

Recovery and malleability

Recovering the signer

Ethereum doesn't send the public key. It rearranges the signing equation. Since s·R = z·G + r·Q:

Q = (s × R - z × G) / r

address = last 20 bytes of keccak256(Q.x || Q.y)

The x coordinate of R is r, but two y values are possible. v (27 or 28) says which one. Recovery usually returns an address even when the message is wrong, so the code must always compare the result with the expected signer. The contract does so with issuers[signer].active.

Malleability

Negating k flips R to −R, which has the same x. So:

(r, s, v)  and  (r, n - s, flipped v)  are both valid for the same message and key

Anyone can compute the twin without the private key. OpenZeppelin's ECDSA.recover rejects any s above n / 2, which leaves each signature with just one accepted form.

In the code: CertificateRegistry.sol:73, and OpenZeppelin's ECDSA.sol:134.

EIP-712

Used for: batch approvalSigning method: eth_signTypedData_v4

EIP-712 defines how to hash structured data so that wallets can display it and the signature only works in one place.

typeHash(Batch)  = keccak256("Batch(bytes32 root,uint32 count)")
structHash       = keccak256(typeHash || root || count)

domainSeparator  = keccak256(
    keccak256("EIP712Domain(string name,string version,uint256 chainId,address verifyingContract)")
    || keccak256("AcademicCertificates") || keccak256("1") || chainId || contract )

digest           = keccak256(0x19 || 0x01 || domainSeparator || structHash)

Each value is padded to 32 bytes, and strings are hashed. Different structures can't collide because the type hash is included. The leading 0x19 can't begin a valid transaction encoding, so a signed message can't pass as a transaction.

Commitments and Merkle proofs

Owner: Lokesh. Publishing one hash that covers everything, and revealing only parts of it.

Keccak-256

Output: 256 bitsState: 1,600 bitsRate: 1,088 bitsCapacity: 512 bits

Keccak uses a sponge construction, which differs from SHA-256's Merkle–Damgård design. A large state absorbs input, is scrambled, and then gets squeezed for output.

PadAdd 0x01 … 0x80 to fill 136-byte blocks
→
AbsorbXOR a block into the rate, then run Keccak-f
→
RepeatFor each block
→
SqueezeTake the first 32 bytes

The capacity part of the state is never directly touched by input or output, and it sets the security level. Because of this hidden state, Keccak isn't vulnerable to length extension.

Keccak-256 vs SHA3-256: Ethereum adopted Keccak before NIST finalized SHA-3. SHA3-256 pads with 0x06 where Keccak pads with 0x01, so the two give different outputs for the same input.

Keccak-f[1600]: 24 rounds of 5 steps

The state is a 5 × 5 grid of 64-bit lanes, A[x, y].

StepFormulaPurpose
θ thetaC[x] = XOR of column x
A[x,y] ^= C[x-1] ^ ROTL(C[x+1], 1)		Each bit depends on 11 bits, spreading across columns
ρ rhoA[x,y] = ROTL(A[x,y], r[x,y])Spreads bits within each lane
π piB[y, 2x+3y] = A[x,y]Moves lanes around the grid
χ chiA[x,y] ^= (NOT A[x+1,y]) AND A[x+2,y]The only non-linear step

Security and cost

Preimage resistance is about 2256 and collision resistance is about 2128. On the EVM, it costs 30 gas plus 6 per 32-byte word, which is why on-chain hashing here uses Keccak-256, not SHA-256 (60 gas plus 12 per word).

Salted commitments

HidingBindingSalt: 32 bytes per field
leaf = keccak256(0x00 || abi.encode(string name, string value, bytes32 salt))
  • Binding rests on collision resistance. Opening to a different value would need a collision, costing about 2128 work.
  • Hiding rests on the salt. Without one, the hash of a low-entropy value such as a CGPA falls to about 1,000 guesses. With a 32-byte salt, the attacker must also search 2256 salts.
  • Why ABI encoding: each value gets its length and fixed slots. Packed encoding would make ("ab", "c") and ("a", "bc") identical.

Merkle trees

Proof size: O(log n)Two levels: fields and batch
node       = keccak256(0x01 || low || high)     children sorted by value
batch leaf = keccak256(0x02 || certRoot)
odd node   = moved up unchanged

Building and proving

Build:  while more than one node is left, hash neighbours in pairs
Prove:  at each level, record the sibling of the current position (if any)
Verify: h = leaf;  for each sibling: h = hashNode(h, sibling);  require h = root

Forging a proof needs a second preimage or collision in Keccak-256, as the root fixes the whole tree. Sorted children mean a proof needs no left or right flags. This doesn't lose anything here, since each leaf names its own field.

Three defences in the design

RuleAttack it blocks
Prefixes 0x00, 0x01 and 0x02Second preimage: an inner node's 64 input bytes being presented as a leaf
Odd node promoted, not duplicatedTwo different lists sharing one root (CVE-2012-2459)
Field name inside the leafA value being presented under another field's name

Selective disclosure

Selective disclosure is a protocol that combines the earlier algorithms. The student gives the verifier a presentation file containing the chosen fields, their salts and proofs, plus the certificate root, batch proof and signature.

Verification order

  1. Format and chain: checks the file's shape, chain ID and registry address. A wrong chain or registry gives NOT_ANCHORED.
  2. Field proofs: for each field, leaf + proof must reach certRoot. Failure gives TAMPERED.
  3. Batch proof: batchLeaf(certRoot) + proof must reach batchRoot. Failure gives TAMPERED.
  4. On-chain record: the root must be published. If not: NOT_ANCHORED.
  5. Signature: recovering from the EIP-712 digest must give the batch's recorded issuer. If not: UNKNOWN_ISSUER.
  6. Registry: the issuer must have a name, and it must match a disclosed organizationName. If not: UNKNOWN_ISSUER.
  7. Revocation: the batch and certificate roots must not be revoked. If they are: REVOKED.
  8. PDF: if supplied, AES-GCM decryption and SHA-256 must match the signed hash. If not: TAMPERED.
  9. Result: if every check passes: VALID.

What it does and doesn't hide

  • Hidden: the values of unrevealed fields.
  • Not hidden: the number of fields, the batch size, and the certificate root. The same root in every presentation means verifiers who compare notes can link them.
  • Not provable: statements such as "CGPA is at least 8" without revealing the value. That needs zero-knowledge proofs, which are future work.
