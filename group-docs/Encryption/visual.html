2. Inside GCM

GCM has two parts. Counter mode provides confidentiality, and GHASH produces the tag. This table rebuilds the ciphertext from section 1 using only AES and XOR.

BlockCounterKeystream = AES(key, counter)PlaintextCiphertext = keystream XOR plaintext
  1. Counter blocks: the 12-byte IV is followed by a 4-byte counter. Counter 1 is kept for the tag, and data starts at counter 2.
  2. Keystream: AES encrypts each counter block. AES only ever runs forward, even when decrypting.
  3. Encrypt: the keystream is XORed with the plaintext. Decrypting does the same XOR.
  4. Tag: GHASH combines the AAD and ciphertext, then the result is masked with AES(key, counter 1). A wrong tag means no output at all.

3. Why the mode matters

The same AES key can hide a document or leak its layout, depending on how it's used. This is a real AES encryption of the image's pixels. Each 16-byte block is drawn as one shade, taken from its first encrypted byte.

4. Why an IV must never repeat under one key

Two messages are encrypted with the same key and the same IV. An attacker who has never seen the key XORs the two ciphertexts.

C1 XOR C2 (the keystream cancels out, leaving P1 XOR P2)

Reusing an IV in GCM also weakens the authentication key, so forgery becomes possible too. The project avoids this by using a new key per PDF and a random 96-bit IV per message.

5. Sealing credentials in SQLite

This matches seal() on the server. One key in server/data/secret.key protects every row, and each value gets its own IV.

Row 1 in credential_sealed: iv.tag.body

Row 2, same text

Identical text gives different stored values, because the IV is new each time. So nobody can tell from the database that two rows hold the same data.
